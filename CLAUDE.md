@AGENTS.md

# Context

Personal portfolio tracker. The full specification is in PROJECT_SPEC.md: read it before any large task. Deviations from the spec and open notes: docs/decisions.md. Supabase operations (environments, keys, inviting people): docs/supabase-setup.md.

# Rules

- Strict TypeScript. No `any` without a justification.
- lib/engine is PURE: no Supabase imports, no fetch, no implicit Date.now() (take "today" as a parameter). ESLint enforces it (eslint.config.mjs).
- Money uses decimal.js (the isolated `D` constructor in lib/engine/decimal.ts); never float arithmetic for persisted amounts.
- Every schema change is a new migration in supabase/migrations. **Every migration that creates a table includes its GRANTs and its RLS**: default privileges on `public` are revoked for `anon` and `authenticated`.
- Every new engine calculation gets Vitest tests, edge cases included.
- Validate inputs with Zod on the server.
- Never expose SUPABASE_SECRET_KEY to the client. It bypasses RLS: `lib/db/admin.ts` is `server-only` and is used only for work that doesn't belong to a user (crons, creating instruments, the sign-in code attempt limit in `lib/db/login-attempts.ts`, which runs before there is a session), never to serve a user's reads or writes.
- On the server the session is verified with `getClaims()`, never `getSession()`. The proxy is not an authorization barrier: every page or action verifies again, and RLS protects the data.
- Supabase only in the cloud (no Docker, no local stack): `finance-dev` for development and `finance` for production (Phase 7). Don't `supabase link` or `db push` to `finance` without an explicit request; the `pnpm db:*` scripts refuse to run if the linked project isn't the development one.
- Never `supabase config push` without first running `pnpm db:config-diff` and reviewing the diff: without a TTY the CLI applies changes without asking. `supabase/config.toml` declares only what we manage (it is not the `init` template).
- Integration tests (`pnpm test:integration`) run only against `finance-dev` (they refuse any other project) and don't run in CI.
- Crons (`/api/cron/*`): public to the proxy, protected only by `Authorization: Bearer ${CRON_SECRET}` with a constant-time comparison; they fail closed if the secret is missing or short (`lib/cron/`). They use `lib/db/admin.ts` (a cron is not a user). Jobs receive "today" as a parameter.
- Everything a data provider returns is untrusted input: validated with Zod and sanitized (`lib/market-data/`). Provider amounts are decimal strings, never floats.
- PostgREST caps responses at 1000 rows: reads that can exceed that (transaction history, one instrument's series) are paginated with `.range()`. Series for several instruments are read with the `price_series` RPC (`getCloseSeries`: one row per instrument, one call per 50), never with one query per instrument.
- `numeric` columns are read as text (`column::text`) and enter the engine through `d()`; every row is validated with Zod at the boundary (`lib/portfolio/rows.ts`). On write, the number is built in `lib/portfolio/mappers.ts` (the form's digit limits make it exact).
- All money shown to people is formatted with `lib/portfolio/format.ts` (es-UY, Montevideo time); never loose `toFixed`/`toLocaleString` in components. Gain and loss: `<Pnl>` (color + sign + arrow).
- Every Server Action and Route Handler: `getSessionUser()` (uses `getClaims()`), Zod on the input, generic errors to the outside (details to `console.error`), and a database rate limit (`takeRateLimit`) if it calls an external service. The secret key is only for creating instruments and writing quotes.
- Adding, editing and deleting transactions go through `validateLedgerChange` before saving.
- The historical series, TWR, XIRR and benchmark belong to the pure engine (`lib/engine/{dates,series,returns,performance}.ts`); reading closes and formatting live in `lib/portfolio/`. Stored closes are split-adjusted: they are un-adjusted with the ledger's `SPLIT` entries, not with `corporate_actions`. XIRR uses `number` (it is a rate for display, not an amount). The benchmark (`SPY`) is one more instrument maintained by the jobs (`active_instruments()` includes it). With "Actualizar precios", today's quote is the last point of each series when it is from a day after the last close (`lib/portfolio/live-series.ts`, without touching the engine): all or nothing together with the benchmark, and the button also refreshes the benchmark (`refresh-targets.ts`). The value of the series' last row must equal the total value on Home (`performance-live.test.ts`).
- Client components don't import `lib/engine` or `lib/portfolio/format.ts` (they would drag decimal.js into the browser): they receive text and `number`s prepared on the server (`performance-view.ts`, `allocation-view.ts`) and use `chart-format.ts`, `pnl-text.tsx`.
- CSV import: two formats recognized from the headers (`lib/importers/detect.ts`): our own **simple** format (`simple.ts`, the same one "Exportar CSV" writes, `source = 'csv'`) and **Delta** (`delta.ts`, `source = 'delta_csv'`). The template (`template.ts`) and "Exportar CSV" are tested against the parser (round trip): changing a column means touching all three. New symbols in the simple format are verified with the provider before they are created (`import-flow.ts`); rows that look like repeats of loaded transactions are excluded by default (`import-similar.ts`). Every imported transaction carries its `import_id` and a whole import can be undone (`undo_import`, validated first with `LedgerChange` `removeMany`). The preview (`import-preview.ts`) sends the client preformatted text. User guide: `docs/importar-csv.md`.
- Adding a buy or sell: when the symbol is chosen, `TransactionForm` calls `getReferencePrice` (`lib/portfolio/reference-price.ts` validates and formats; it reuses the `search_symbols` limit) and fills the price with the current quote without overwriting what the person already typed. `SymbolCombobox` opens its list with `position: absolute`: it can't live inside a container with clipped `overflow` (the Watchlist card uses `overflow-visible` for that reason). On phones, `<input type="date">` fields go one per row: the iPhone's doesn't shrink below ~183 px.
- Asset detail (`positions/[symbol]`, a position or a followed symbol): "Evolución del precio" (`price-range-section.tsx` + `price-range-chart.tsx`, client), "Datos de la empresa" and "Ganancias", each in its own `<Suspense>`. The logic is pure and tested (`range-chart.ts`, `company-view.ts`, `earnings-view.ts`); the client doesn't import `lib/engine` (it uses `range-options.ts` and `chart-format.ts`). 1Y comes from `prices_daily` + today's quote (`withLiveBar`); 1W and 1M from Yahoo intraday bars through the `getRangeSeries` Server Action (session, Zod, `search_symbols`, only symbols already in the database) with a fallback to daily closes (`range-data.ts`). Company data and bars are cached with `unstable_cache` (`company-data.ts`: 1 h and 5 min; failures aren't cached) and validated field by field with Zod (`yahoo-company.ts`): a broken field stays empty instead of taking down the rest. Large quantities are written in words (`formatCompact`); `niceScale` picks the decimals depending on whether the step is exact (2.5 gets one decimal).
- "Antes de comprar" (asset detail, `before-buy-section.tsx` + `before-buy-card.tsx`, in its own `<Suspense>`): the calculation belongs to the pure engine (`lib/engine/what-if.ts`), text and amounts to `before-buy-view.ts`, reads to `before-buy-data.ts` (only `prices_daily` with `adj_close`, no Yahoo). The portfolio is evaluated with today's weights and the last year of returns; a position with a short history is left out with a notice (only the symbol being viewed shortens the window). The chart receives points per dollar per month and the client multiplies by the amount. Every instrument keeps at least 5 years of closes (`desiredStart`). It is not a buy recommendation and the card says so: no "buy" verdicts.
- Multiple portfolios (1 to 5 per person, each with **one** hidden account): the one being viewed comes from `getPortfolioContext` (`lib/portfolio/current-portfolio.ts`; the `pt-portfolio` cookie is always checked against `listPortfolios` under RLS; never trust the cookie). There is no "main account": every screen receives its `PortfolioRef` and `loadPortfolioSnapshot(client, portfolio)`. A transaction is edited or deleted in **its** portfolio (`getTransactionRow` returns its account); additions and imports go to the one chosen in the form (`resolveChosenPortfolio`). The limit, the names and "don't delete the last one" are enforced by the database (migration `multiple_portfolios`, codes `MP001`/`MP002`). With a single portfolio no selector is shown. "Todo junto" (cookie `all`, `PortfolioScope` `{ kind: "all" }`): **never** combine transactions from several accounts in one engine call (average cost is per account and each account's `SPLIT` would be applied twice); each part is computed (`snapshot.parts`) and added with `combineEngineResults` / `combineSeries` (`lib/engine/combine.ts`). Screens load with `loadScopeSnapshot(client, context.scope)`; `context.current` is the portfolio for additions and imports (`null` with "Todo junto": it must be chosen).
- Crypto: `instruments.type = 'CRYPTO'`, canonical symbol `BTC-USD` (never `BTC`: that is an ETF). Only `-USD` pairs from Yahoo's `CCC` exchange. Type labels come from `typeLabelOf` (`lib/portfolio/instrument-type.ts`, no imports: the client uses it). A portfolio's benchmark is one of `BENCHMARKS` (`lib/portfolio/benchmarks.ts`: SPY or BTC-USD) and its name comes from `benchmarkLabel`. The series grid is business days and only the last point can fall on a weekend (`series.ts`); on a weekend the live point doesn't require the stock benchmark (`live-series.ts`). Chart axes take the width of their longest tick (`axisWidthFor`): there are six-figure prices.
- Every action that can leave a new instrument without prices (importing, saving a transaction with a symbol, "Actualizar precios") calls `backfillPendingInBackground` (`lib/portfolio/background.ts`): it downloads the history without blocking the response.

- Sign-in is with a 6-digit code sent by email (`/login`, Server Actions `requestCode` and `verifyCode`); there is no link and no return path. `otp_length` in `supabase/config.toml` and `CODE_LENGTH` in `lib/validation/login.ts` must match. Every verification goes through `takeLoginAttempt` first (5 per 15 minutes per email). SMTP (an app password) is set only in the Supabase dashboard: it is not declared in `config.toml` and never pasted into a chat.
- **There are no passwords:** the `strip_user_password` trigger (migration `no_passwords`) deletes the hash in `auth.users` every time Auth writes one, because Supabase's public API lets a user set one and sign in without going through `takeLoginAttempt`. Password, passkey or OAuth sign-in is a separate security decision, not an add-on. Tests sign in with `generateLoginCode` + `verifyOtp`, never `signInWithPassword`. The email subject contains the code (`{{ .Token }}`).
- Session cookies are `HttpOnly` and, over HTTPS, `Secure` (`lib/db/cookie-options.ts`, used by `lib/db/server.ts` and `lib/db/proxy.ts`): there is no Supabase client in the browser and no code reads `document.cookie`. If one is ever added, this must be revisited.
- Public to the proxy (`lib/db/auth-routes.ts`): `/login`, `/api/cron/*`, `/pwa/*`, `/sw.js`, `/manifest.webmanifest` and `/api/widget` (the last three exact). Apart from `/api/widget`, none of these carries anyone's data.
- iPhone widget (Scriptable, `lib/widget/`, `docs/widget-iphone.md`): `/api/widget` has no session; it is protected by a personal read-only code (`Authorization: Bearer`, never in the URL; the database stores only its SHA-256, `widget_tokens`). It is the **only** exception to the `admin.ts` rule: for a person's data, the secret key calls only `widget_ledger` (executable only by `service_role`), which determines whose data it is from the token; everything else it touches is market data. Never read user tables with the secret key, because `queries.ts` filters only through RLS. The snapshot is built with `snapshotFromRows`, the same as Home. `?portfolio=<name>` (the widget's "Parameter" field) chooses a portfolio and `widget_ledger` validates it. New codes work for every portfolio (the app no longer offers choosing one when creating it); single-portfolio codes are older and the database still honors them. The script template contains no backslashes (they get lost; `script.test.ts` guards it). Before calculating, it asks Yahoo, in one call, for the quotes of its positions that are 2 hours old or more (`quotes.ts`: `quotes_latest.fetched_at` is set by a trigger; one attempt per code every 10 minutes with `take_widget_quote_refresh`; if it fails or takes more than 5 s, it shows what is stored and never throws). The response (`view.ts`) is preformatted text read by the script (`script.ts`, the same for everyone, without the code): the script lives on phones and is updated by hand, so new fields are **added** without removing or changing existing ones (the script must tolerate missing ones); `WIDGET_VIEW_VERSION` is bumped in both only if the shape breaks. `script-run.test.ts` runs the script against a Scriptable mock.
- PWA: the service worker (`public/sw.js`) **doesn't cache pages or financial data**, only the offline screen; when a precached file changes, bump its `VERSION`. The last known state lives in `localStorage` (preformatted text, `lib/portfolio/snapshot-cache.ts`) and is cleared on reaching `/login`. Dark mode follows the system with CSS (`prefers-color-scheme`), not the `.dark` class.
- Home (`app/(app)/page.tsx`): performance is requested **once** (`loadPerformanceOutcome`, a promise that never rejects) and shared by three sections, each with its own `<Suspense>` (chart, monthly, risk: `components/app/performance-section.tsx`). Gain curves, risk and monthly returns belong to the pure engine (`lib/engine/{performance,risk,monthly}.ts`); text and tones to `performance-view.ts` and `contribution-view.ts`. Total gain is `total value − deposits + withdrawals` and is hidden if any price is missing.
- Security headers and CSP: `next.config.ts` and `lib/security/csp.ts`. The CSP (production only) allows only the app's own origin (`connect-src 'self'`, no Supabase client in the browser): if a component needs to load anything from another domain (image, font, script, connection), it must be added there deliberately and with a test. Inline scripts and styles stay allowed until the strict nonce-based CSP (Phase 7). Accepted residual risks from the security review: `docs/decisions.md`, "Revisión de seguridad".
- A button that switches from `type="button"` to `type="submit"` in the same place in the React tree submits the form in the middle of the same click: each branch gets its own `key` (see `components/app/watchlist-row-footer.tsx`).
- Vercel: never run `vercel` without checking what it uploads (it doesn't honor the whole `.gitignore`); `.vercelignore` leaves out fixtures, `docs/`, the spec, tests and `supabase/`. Production variables: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` and `CRON_SECRET` (the `NEXT_PUBLIC_*` ones are baked in at build time: set them before deploying). They are loaded over stdin from `.env.local` (`... | vercel env add NAME production --sensitive`), without printing them. The Phase 6 Vercel project points at `finance-dev`; production is Phase 7.

# Conventions

- Identifiers in English; code comments in Spanish, only where the why isn't obvious; docs and UI text in Spanish. The README, PROJECT_SPEC.md, this file and commit messages are in English.
- Commit messages: English, imperative subject ("Add …", "Fix …"), no co-author or AI attribution trailers.
- The repository is public. Never commit real investment history, screenshots of a real portfolio, or data from `finance-dev`. README images (`docs/images/`) come from a temporary demo account that is deleted afterwards.
- Allowing a person in: `insert into public.allowed_emails (email) values ('...')` (see docs/supabase-setup.md).

pnpm db:push            # migrations to finance-dev
